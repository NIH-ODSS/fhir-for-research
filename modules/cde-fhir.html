CDEs & FHIR

min. reading time 
Last updated: October 26, 2026
Roles: Investigator Research Leaders Informaticist Software Engineer Clinician Scientist/Trainee
Learning objectives
  1. Distinguish how Common Data Elements, Common Data Models, and FHIR contribute to interoperability.
  2. Describe how connecting CDEs with FHIR and related interoperability standards creates a pathway from standardized research definitions to reusable, computable research infrastructure.
  3. Describe the complementary layers of a computable CDE architecture.
  4. Identify common interoperability patterns for a CDE-based research workflow.

1 FHIR and interoperable research

Interoperability requires both shared meaning and a standardized way to represent and exchange data. Common Data Elements (CDEs), Common Data Models (CDMs), and HL7 Fast Healthcare Interoperability Resources (FHIR) address different parts of this challenge:

  • CDEs standardize what data mean and, where specified, what is collected.
  • CDMs standardize how data are organized for a particular use or analytical environment.
  • FHIR standardizes how health information can be represented and exchanged between systems. It can be viewed as a specific type of CDM, though FHIR also has many capabilities that go beyond CDMs (e.g., the FHIR API).

FHIR provides a standards-based framework for representing and exchanging health and research information using FHIR resources, profiles, terminology bindings, and APIs. When combined with well-defined CDEs, these capabilities can help translate shared research concepts into machine-actionable specifications that software systems can implement and use to validate and exchange data.

FHIR does not, however, create semantic interoperability by itself. A FHIR representation still requires clearly defined concepts, appropriate terminology and value-set bindings, explicit context and constraints, governance, and implementation guidance.

The goal is not simply to “convert CDEs to FHIR.” It is to create an interoperable semantic and technical layer in which CDEs can be consistently represented, validated, exchanged, and reused across research workflows.

2 FHIR-enabled CDEs

2.1 Bridging the gap for computability

Historically, CDEs have been represented through data dictionaries, case report forms, PDFs, metadata repositories, and spreadsheet-based specifications. Existing repositories also provide structured metadata and machine-readable exports of CDEs, as described in the CDE introduction. These artifacts can effectively define research concepts, but they do not necessarily provide everything software systems need to implement those concepts consistently.

FHIR and related implementation standards provide a machine-readable implementation layer that can help bridge the gap from human-readable definitions to computable assets. A FHIR-enabled CDE combines its scientific and semantic definition with computable specifications for how the element can be represented, constrained, validated, and exchanged.

2.2 Example: a CDE for pain intensity

Consider a CDE for pain intensity.

A traditional CDE might specify:

  • the element name and definition;
  • question or prompt text; and
  • permissible values or response options.

A FHIR-enabled implementation makes choices such as the following explicit and usable by software, building on terminology and constraints already present in the CDE definition:

  • a code from a standard terminology, such as Logical Observation Identifiers Names and Codes (LOINC), when appropriate;
  • the applicable FHIR resource and profile, which define the structure used to represent the concept;
  • terminology and value-set bindings;
  • cardinality (how many times a data element may occur) and other validation constraints; and
  • a standards-based representation that can be exchanged through a FHIR API.

The underlying scientific concept has not changed. What changes is how computable the data element is (i.e., how consistently software can implement it). A shared computable specification reduces the need for each organization or software team to interpret the CDE independently and provides rules that systems can use to process and validate data.

2.3 What FHIR enables

FHIR is not a replacement for CDEs. Instead, it provides a standards-based pathway for operationalizing CDEs so they can move beyond reference definitions and become reusable components of interoperable research systems.

The table below explains how CDEs and FHIR may support complementary capabilities for research interoperability. These capabilities reinforce one another, underscoring how semantic and technical interoperability should be developed together.

Research interoperability capability Purpose Examples
Standardized CDEs Establish shared meaning Define research concepts, data definitions, response options, and applicable terminology consistently.
Computable CDEs Make definitions machine-actionable Represent CDE specifications in structured, machine-readable forms with explicit terminology, constraints, and validation requirements.
Semantic interoperability Preserve meaning across systems Use common definitions, terminology bindings, mappings, and value sets so that exchanged data can be interpreted consistently.
Technical interoperability Enable standards-based exchange Use FHIR resources and profiles, APIs, Structured Data Capture (SDC), Bulk Data Access, terminology services, and implementation guides to support implementation across systems.
Computable research workflows Put standards into practice Reuse computable CDEs in workflows such as electronic data capture, eSource (for example, populating research forms from electronic health records [EHRs]) [1], cohort and phenotype definitions, computable protocols, and EHR-to-research data exchange.
SI-enabled research Build on standardized, computable data Provide well-defined, structured data that can support SI and analytics workflows. Standardization does not by itself establish data quality or model validity.

3 Computable CDE architecture

Implementing a computable CDE across systems requires more than a machine-readable definition or a single FHIR resource. It typically involves a coordinated set of semantic and technical artifacts that preserves the meaning of a research concept while supporting consistent implementation, validation, exchange, and reuse. The table below describes these complementary layers.

CDE architecture Purpose
1. Semantic definition
What does the CDE mean?		 Defines the research concept, question or variable, permissible values, units, context, and other metadata needed for consistent interpretation.
2. Terminology
How is meaning coded consistently?		 Links concepts, responses, and units to appropriate standard terminologies such as LOINC, SNOMED CT, RxNorm, International Classification of Diseases (ICD), and Unified Code for Units of Measure (UCUM). Value sets identify applicable codes for a particular element, along with a binding strength that determines how strictly the value set constraints are applied.
3. Computable representation
How can software interpret the CDE?		 Represents CDE specifications in structured, machine-readable formats. FHIR profiles use StructureDefinition resources to specify constraints; ValueSet, CodeSystem, and ConceptMap resources represent terminology artifacts. Other schema languages, such as LinkML, can also represent structured definitions.
4. Data collection
How is the CDE captured?		 Translates standardized definitions into reusable electronic instruments. FHIR Questionnaire and QuestionnaireResponse, together with the HL7 Structured Data Capture (SDC) Implementation Guide, can support standardized forms, response options, validation, and conditional logic.
5. Exchange and access
How do systems share the data?		 FHIR APIs and implementation guides define how standardized data can be accessed and exchanged. SMART on FHIR supports authorized application access and integration. The FHIR Bulk Data Access Implementation Guide supports population-level export without individual patient-by-patient API calls.
6. Mapping and reuse
How does the CDE connect to other data models?		 Mappings connect CDEs to clinical, research, public health, and analytical representations, including CDMs. ConceptMap supports mappings between codes; moving data between models also requires structural transformation rules. Explicit, validated mappings reduce repeated local transformation and support reuse across environments.
NoteStructured Data Capture Implementation Guide

The HL7 Structured Data Capture (SDC) Implementation Guide provides guidance for using FHIR Questionnaire resources in more sophisticated data-collection workflows. A Questionnaire can represent CDE questions, response options, terminology bindings, instructions, validation constraints, and conditional behavior.

This approach is particularly relevant to standardized assessments and patient-reported outcomes, where consistent questions, response options, scoring rules, and terminology are important for reuse.

This implementation guide creates a potential pathway from a standardized CDE definition to a reusable electronic data-collection specification. The same computable definition can inform implementation in research applications, registries, EHR-integrated workflows, and other data-collection systems, although individual platforms may require additional integration or transformation.

3.2 FHIR resources for research CDEs

The appropriate FHIR representation depends on the CDE and its use case. Commonly relevant resources include:

  • Questionnaire defines questions and structured data-collection instruments.
  • QuestionnaireResponse represents responses to a questionnaire.
  • Observation represents measurements, assessments, and other observations.
  • Condition represents clinical conditions, diagnoses, and health concerns.
  • ResearchStudy represents information about a research study.
  • ResearchSubject represents an individual’s participation in a study.

Computable CDEs can support several complementary interoperability patterns. A research workflow may use several of these patterns together. For example, terminology-bound CDEs represented in a FHIR Questionnaire for data collection may also be mapped to an analytical CDM for downstream analysis.

Common interoperability patterns Example enabling standards and tools
Questionnaire-driven data capture FHIR Questionnaire, QuestionnaireResponse, SDC
EHR-to-research data access FHIR APIs, SMART on FHIR, Bulk Data Access
Terminology-linked CDEs LOINC, SNOMED CT, RxNorm, UCUM, ValueSets
Machine-readable specifications FHIR profiles, StructureDefinitions, ValueSets, LinkML
Cross-model reuse ConceptMaps for concept relationships, together with explicit structural transformation rules
Standards-based implementation FHIR implementation guides and profiles

3.3 Terminology bindings and services

Terminology links connect CDE concepts and permissible values to standardized vocabularies and codes. In FHIR, a terminology binding associates a coded element with a value set and specifies how strictly it must be followed. For example, a measurement may use LOINC to identify what was measured, UCUM to represent the unit, and a value set to identify appropriate coded responses. Other terminologies, including SNOMED CT, RxNorm, and ICD, may also be used, depending on the concept.

Terminology binding strengthens semantic interoperability. Consistent implementation also requires appropriate context, constraints, profiles, mappings, governance, and version management.

FHIR terminology services can support value-set expansion, code validation, terminology lookup, and concept mapping. Examples include open-source software such as HAPI FHIR, Snowstorm, and Cartos (see below). There are also commercial products in this space, such as the Health Language Platform. Supported operations and terminology content vary by implementation. For more detail on code systems, value sets, and mappings, see the Terminology and FHIR module.

NoteCartos terminology service

The Office of the National Coordinator for Health IT (ONC) provides Cartos for accessing terminology associated with its Health IT Certification Program, Standards Version Advancement Process (SVAP), and supported implementation guides.

Implementers can browse the content without an account or use a read-only FHIR R4 API to search, retrieve, expand, look up, and validate supported terminology content. Selected terminology collections are also available for download.

Cartos focuses on this program-related content; it does not necessarily distribute complete large clinical code systems already available through their respective terminology stewards.

4 Progress toward FHIR-enabled CDEs and datasets

FHIR-based access to EHR data provides a starting point for implementing research CDEs. For example, REDCap Clinical Data Interoperability Services (CDIS) supports authorized imports of selected EHR data, including demographics, vital signs, laboratory results, medications, problems, and procedures. Availability depends on local configuration and source-system support. Importing these data still requires checking whether their definitions, units, timing, and context match the research CDE. See the REDCap on FHIR module for details.

Other efforts, such as patient-reported outcomes, clinical trial data capture, registries, adverse event reporting, and capture of real-world evidence, are still emerging with varying levels of maturity and adoption of FHIR-enabled CDEs. For example, the HL7 Vulcan Accelerator has published implementation guidance for adverse events and real-world data, while the Vulcan Interoperability Bridge supports demonstrations of connected research workflows. (The HL7 Vulcan Accelerator module explores these efforts in more detail.) Other areas are less mature, including behavioral measures, disease-specific outcome measures, and research-specific instruments. Scaling FHIR-enabled CDEs across all domains can be difficult due to the need for custom FHIR profiles, extensions, and terminology work.

Adams et al. highlight limitations for scaling CDEs in their 2025 paper, The NIH HEAL pain common data elements (CDE): A great start but a long way to the finish line [2]. The findings recognize that while FHIR can standardize the collection, representation, and exchange of CDEs, it does not automatically solve for interpretation, contextual validity, and population-specific meaning. The authors emphasize that timing, pain type, disease context, and population matter, and that the same measure may not mean the same thing across studies. This paper concludes that future computable CDEs will need FHIR representations, metadata, provenance, implementation guidance, and validation constraints – not merely exchange standards. The opportunity for the research community is to create a computable layer that preserves meaning, context, and validity as data move across studies, institutions, and SI-enabled research workflows.
